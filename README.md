## Current Application Overview

This application is a small REST API for managing `CashCard` records. Even though the domain is simple, the project already demonstrates the main moving parts of a production-style Spring Boot backend:

- Spring Boot starts and wires the application.
- Spring MVC handles HTTP requests and routes them to controller methods.
- Spring Security authenticates users and enforces route-level access rules.
- Spring Data JDBC generates repository implementations from interfaces.
- H2 stores the application data during tests.
- `@SpringBootTest` runs the real application and exercises the full stack with HTTP requests.

One important clarification up front:

- Java is the language the app is written in.
- Spring is what performs dependency injection, bean creation, request mapping, security checks, and repository generation.
- So when we say something is "injected," it is Spring doing that work, not Java by itself.

## Bottom-To-Top Architecture

### 1. Spring Boot Starts the Application

The entry point is `src/main/java/example/cashcard/CashCardApplication.java`:

```java
@SpringBootApplication
public class CashCardApplication {
	public static void main(String[] args) {
		SpringApplication.run(CashCardApplication.class, args);
	}
}
```

`@SpringBootApplication` tells Spring Boot to:

- start component scanning
- create the application context
- auto-configure common infrastructure
- start the embedded web server

Because this project includes Spring Web, Spring Security, Spring Data JDBC, and H2, Spring Boot auto-configures all of those pieces when the application starts.

### 2. The Test Layer Runs the Real Application

The main integration tests are in `src/test/java/example/cashcard/CashCardApplicationTests.java`:

```java
@SpringBootTest(webEnvironment = SpringBootTest.WebEnvironment.RANDOM_PORT)
class CashCardApplicationTests {
    @Autowired
    TestRestTemplate restTemplate;
}
```

This annotation matters a lot:

- `@SpringBootTest` starts the full Spring application context.
- `webEnvironment = RANDOM_PORT` starts the embedded server on a random port.
- Spring creates a `TestRestTemplate` that talks to that running server.

That means these tests are not calling controller methods directly. They send real HTTP requests into the running application. Because of that, every request goes through:

- security filters
- request mapping
- JSON serialization and deserialization
- controller logic
- repository logic
- database access

That is why these are integration tests, not simple unit tests.

### 3. Where Test Data Comes From

The database schema is defined in `src/main/resources/schema.sql`:

```sql
CREATE TABLE cash_card
(
    ID     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    AMOUNT NUMBER NOT NULL DEFAULT 0,
    OWNER  VARCHAR(256) NOT NULL
);
```

The test data is loaded from `src/test/resources/data.sql`:

```sql
INSERT INTO CASH_CARD(ID, AMOUNT, OWNER) VALUES (99, 123.45, 'sarah1');
INSERT INTO CASH_CARD(ID, AMOUNT, OWNER) VALUES (100, 1.00, 'sarah1');
INSERT INTO CASH_CARD(ID, AMOUNT, OWNER) VALUES (101, 150.00, 'sarah1');
INSERT INTO CASH_CARD(ID, AMOUNT, OWNER) VALUES (102, 200.00, 'kumar2');
```

During tests, Spring Boot creates an embedded in-memory H2 database, builds the `cash_card` table, and loads those rows before the tests run.

That is why the tests already know that:

- `99`, `100`, and `101` belong to `sarah1`
- `102` belongs to `kumar2`

### 4. Security Is Checked Before the Controller Runs

Security is configured in `src/main/java/example/cashcard/SecurityConfig.java`.

The important part is:

```java
@Bean
SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http
            .authorizeHttpRequests(request -> request
                .requestMatchers("/cashcards/**")
                .hasRole("CARD-OWNER"))
            .httpBasic(Customizer.withDefaults())
            .csrf(csrf -> csrf.disable());

    return http.build();
}
```

This means:

- every request to `/cashcards/**` must come from an authenticated user
- that user must have the role `CARD-OWNER`
- authentication uses HTTP Basic auth

Users are defined in memory in the same config class:

```java
@Bean
UserDetailsService testOnlyUsers(PasswordEncoder passwordEncoder) {
    ...
}
```

Those test users include:

- `sarah1 / abc123 / CARD-OWNER`
- `kumar2 / xyz789 / CARD-OWNER`
- `hank-owns-no-cards / qrs456 / NON-OWNER`

### 5. When Authentication and Authorization Happen

For each HTTP request, the sequence is roughly:

1. The request hits the Spring Security filter chain first.
2. Spring Security reads the `Authorization` header.
3. With Basic Auth, it decodes the username and password.
4. It loads the user from `UserDetailsService`.
5. It verifies the password using the configured `PasswordEncoder`.
6. If the credentials are wrong, Spring returns `401 UNAUTHORIZED`.
7. If authentication succeeds, Spring checks the authorization rule for the route.
8. If the user lacks the required role, Spring returns `403 FORBIDDEN`.
9. Only after those checks pass does the request continue to the controller.

So the controller does not run at all when authentication fails or when the role check fails.

That is why:

- bad credentials return `401`
- authenticated users without `CARD-OWNER` return `403`

### 6. How the Controller Is Wired

The controller is in `src/main/java/example/cashcard/CashCardController.java`:

```java
@RestController
@RequestMapping("/cashcards")
class CashCardController {
    private final CashCardRepository cashCardRepository;

    private CashCardController(CashCardRepository cashCardRepository) {
        this.cashCardRepository = cashCardRepository;
    }
}
```

This shows constructor injection.

At startup:

- Spring creates the repository bean
- Spring creates the controller bean
- Spring injects the repository into the controller constructor

This is application-startup dependency injection.

### 7. What Gets Injected at Startup vs Per Request

There are two different kinds of "injection" happening in this application.

#### Startup-Time Bean Injection

Spring creates long-lived beans such as:

- `SecurityFilterChain`
- `UserDetailsService`
- `PasswordEncoder`
- `CashCardRepository`
- `CashCardController`
- `TestRestTemplate` in the test context

Examples:

- Spring injects `PasswordEncoder` into the `testOnlyUsers(...)` bean method.
- Spring injects `CashCardRepository` into the controller constructor.
- Spring injects `TestRestTemplate` into the `@Autowired` field in the test class.

#### Per-Request Argument Resolution

Controller method parameters such as these are resolved for each incoming request:

- `@PathVariable Long id`
- `@RequestBody CashCard newCashCardRequest`
- `Principal principal`
- `Pageable pageable`
- `UriComponentsBuilder ucb`

These are not application-singleton beans. Spring MVC and Spring Security build or resolve them at request time.

### 8. How `Principal` Injection Works

The `Principal` parameter appears in several controller methods, including delete:

```java
@DeleteMapping("/{id}")
private ResponseEntity<Void> deleteCashCard(@PathVariable Long id,
        Principal principal) {
    ...
}
```

This is what happens:

1. Spring Security authenticates the request.
2. Spring Security stores the authenticated user in the security context for that request.
3. Spring MVC sees that the controller method needs a `Principal`.
4. Spring resolves that `Principal` from the current authenticated user.
5. The controller receives it as a method argument.

So `principal.getName()` returns the current username, such as:

- `sarah1`
- `kumar2`

That is how the controller knows who is making the request without the client having to send the owner name in the body.

### 9. What the Controller Actually Does

The controller contains the HTTP-facing application logic.

Examples:

- `@GetMapping("/{requestedId}")` reads one card for the current owner
- `@GetMapping` lists cards for the current owner
- `@PostMapping` creates a new card and forces the `owner` to be the authenticated user
- `@PutMapping("/{requestedId}")` updates a card only if the current user owns it
- `@DeleteMapping("/{id}")` deletes a card only if the current user owns it

The delete method is:

```java
@DeleteMapping("/{id}")
private ResponseEntity<Void> deleteCashCard(@PathVariable Long id,
        Principal principal) {
    if (cashCardRepository.existsByIdAndOwner(id, principal.getName())) {
        cashCardRepository.deleteById(id);
        return ResponseEntity.noContent().build();
    }

    return ResponseEntity.notFound().build();
}
```

This is an important pattern in the app:

- security handles route-level access first
- the controller then performs ownership-level checks for the specific record

That is why an authenticated card owner can still receive `404 NOT FOUND` for a card they do not own.

### 10. The Repository Layer

The repository is defined in `src/main/java/example/cashcard/CashCardRepository.java`:

```java
interface CashCardRepository extends CrudRepository<CashCard, Long>,
    PagingAndSortingRepository<CashCard, Long> {
    CashCard findByIdAndOwner(Long id, String owner);
    boolean existsByIdAndOwner(Long id, String owner);
    Page<CashCard> findByOwner(String owner, PageRequest pageRequest);
}
```

There is no handwritten implementation class.

Instead, Spring Data JDBC reads this interface and generates the implementation automatically when the app starts.

That implementation knows how to:

- save `CashCard` records
- delete by ID
- read by ID
- page and sort results
- derive custom queries from method names

### 11. What `CrudRepository` Gives You

`CrudRepository<CashCard, Long>` provides the basic create, read, update, and delete operations.

That includes methods like:

- `save(...)`
- `findById(...)`
- `deleteById(...)`

Because the generic parameters are `CashCard` and `Long`, Spring Data knows:

- the entity type is `CashCard`
- the primary key type is `Long`

So you get standard data access behavior without writing an implementation by hand.

### 12. What Spring Data JDBC Generates from Method Names

These methods are especially important:

```java
CashCard findByIdAndOwner(Long id, String owner);
boolean existsByIdAndOwner(Long id, String owner);
Page<CashCard> findByOwner(String owner, PageRequest pageRequest);
```

Spring Data parses those method names and derives the needed database queries.

Conceptually, they mean:

- find one row where `id = ?` and `owner = ?`
- check whether a row exists where `id = ?` and `owner = ?`
- find rows where `owner = ?` with paging and sorting

That is how the app enforces ownership without manually writing SQL in the repository interface.

### 13. The Java Model Object

The domain type is defined in `src/main/java/example/cashcard/CashCard.java`:

```java
record CashCard(@Id Long id, Double amount, String owner) {
}
```

This record is used:

- as the object read from the database
- as the object returned by controller methods
- as the request body type for create and update

The `@Id` annotation tells Spring Data which field maps to the primary key.

### 14. The Database Layer

The actual data lives in the H2 database during tests.

At runtime, the flow near the bottom of the stack is:

1. The controller calls the repository.
2. The generated Spring Data JDBC repository runs the needed SQL.
3. H2 stores, updates, deletes, or returns rows.
4. Spring maps those rows back into `CashCard` objects.

So the repository is the abstraction, and H2 is the actual storage engine underneath it.

### 15. End-To-End Flow of a Test Request

Take this delete test as an example:

```java
restTemplate
    .withBasicAuth("sarah1", "abc123")
    .exchange("/cashcards/99", HttpMethod.DELETE, null, Void.class);
```

What happens step by step:

1. JUnit runs the test method.
2. `TestRestTemplate` creates an HTTP `DELETE /cashcards/99` request.
3. It adds Basic Auth credentials for `sarah1`.
4. The request goes to the embedded Spring Boot server.
5. Spring Security authenticates `sarah1`.
6. Spring Security verifies that `sarah1` has the `CARD-OWNER` role.
7. Spring MVC matches the request to `@DeleteMapping("/{id}")`.
8. Spring resolves `id` as `99`.
9. Spring resolves `Principal principal` from the authenticated user.
10. The controller calls `existsByIdAndOwner(99, "sarah1")`.
11. Spring Data JDBC checks the database.
12. The repository returns `true`.
13. The controller calls `deleteById(99)`.
14. Spring Data JDBC deletes the row from H2.
15. The controller returns `ResponseEntity.noContent().build()`.
16. Spring sends back HTTP `204 NO CONTENT`.
17. The test asserts that the response status is correct.

### 16. Why Unauthorized Deletes Return `404`

Now compare that with:

```java
restTemplate
    .withBasicAuth("sarah1", "abc123")
    .exchange("/cashcards/102", HttpMethod.DELETE, null, Void.class);
```

This request is:

- authenticated successfully
- authorized for the `/cashcards/**` route

But card `102` belongs to `kumar2`, not `sarah1`.

So this repository check fails:

```java
cashCardRepository.existsByIdAndOwner(102, "sarah1")
```

The controller then returns:

```java
ResponseEntity.notFound().build();
```

That becomes HTTP `404 NOT FOUND`.

This is intentional. The API avoids leaking whether another user's record exists.

### 17. Why the App Uses Both `401`, `403`, and `404`

Each status code means something different:

- `401 UNAUTHORIZED`: the credentials are missing or wrong
- `403 FORBIDDEN`: the user is authenticated, but is not allowed to access the route
- `404 NOT FOUND`: the route is valid, but the specific record is not visible to this user

In this app:

- bad credentials produce `401`
- `hank-owns-no-cards` produces `403`
- `sarah1` requesting `kumar2`'s card produces `404`

### 18. Why `@DirtiesContext` Matters in Mutating Tests

Tests that create, update, or delete data use `@DirtiesContext`.

That tells Spring to throw away the current application context after the test and rebuild it for later tests.

Why this is needed:

- mutating tests change the database
- later tests expect the original fixture state
- rebuilding the context reloads the schema and test data

Without `@DirtiesContext`, one test could accidentally break another by leaving modified state behind.

## Short Mental Model

If you want one compact way to think about the app, it is this:

1. Spring Boot starts the system.
2. Tests send real HTTP requests into the running app.
3. Spring Security authenticates the user and checks route access.
4. Spring MVC maps the request to a controller method.
5. Spring injects request-specific values like `Principal`, path variables, and request bodies.
6. The controller calls the repository.
7. Spring Data JDBC translates repository operations into database work.
8. H2 stores the rows and returns the results.
9. Spring turns the result into an HTTP response for the client.
